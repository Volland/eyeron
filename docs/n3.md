# Notation3 (N3)

Notation3 is Eyeron's original and primary reasoning language: forward and backward Horn-style rules over an RDF graph, with quoted formulas, generated rules, and proof output.

```
@prefix : <http://example.org/> .

:Socrates a :Man .
{ ?x a :Man . } => { ?x a :Mortal . } .
```

## Highlights

- forward rules with `log:implies` / `=>`;
- goal-directed backward rules with `log:impliedBy` / `<=`;
- generated rules and quoted-formula conclusions;
- proof output with `-p` / `--proof`;
- proof generation and checking in one command with `-c` / `--prove-and-check`;
- RDF 1.1 and RDF 1.2 input profiles for Turtle, N-Triples, N-Quads, and TriG;
- finite RDF Message Log replay and message-at-a-time streaming;
- indexed fact lookup and an agenda path for long single-premise rule chains.

Eyeron supports prefixes and bases, variables, blank nodes, literals, RDF lists, quoted formulas, `log:query`, `log:outputString`, `owl:sameAs` through `=`, virtual `rdf:first` / `rdf:rest` list matching, and deterministic blank nodes generated by repeated rule firings.

- **`string:`** `lessThan`, `greaterThan`, `notLessThan`, `notGreaterThan`, `concatenation`, `contains`, `containsIgnoringCase`, `startsWith`, `endsWith`, `equalIgnoringCase`, `notEqualIgnoringCase`, `format`, `matches`, `notMatches`, `replace`, and `scrape`;

String regular expressions use Rust's Unicode-aware regex engine, with compatibility handling for the look-around forms exercised by the bundled conformance tests.

### Explicit quantification and graph terms

Eyeron accepts the original `@forAll` and `@forSome` declarations:

```n3
@prefix : <http://example.org/>.
@forAll :x.
@forSome :y.
:x :loves :y.
```

This means “everybody loves somebody”: universals precede existentials in
one graph. Declarations must precede its first triple, and `@forAll` must
precede `@forSome`. An IRI may be declared only once in a graph; comma
separated IRI lists are also accepted. Quantified IRIs denote variables in
all triple positions and in nested graph terms. An inner declaration can
shadow an outer one. Prefix and base resolution happen before binding lookup.
Implicit `?x` variables belong to the outermost graph; blank nodes belong
to their innermost graph. These are distinct variables even in `?x :loves _:x`.

To put the existential *outside* a universal, use nesting:

```n3
@forSome :beloved.
{} => { @forAll :person. :person :loves :beloved }.
```

Graph terms retain their local quantifiers. They are closed, referentially
opaque sets of triples, compared up to bijective renaming of local variables
of the same quantifier kind; unused declarations and repeated triples do
not affect their identity. Substitutions reach free variables in nested
graphs and preserve local binders. A closed graph term may therefore be
ground even when its triples contain locally quantified variables.
`log:includes` tests existential consequence, without
instantiating the subject's universally quantified variables.

Universal assertions are instantiated on demand during goal-directed search;
the reasoner does not enumerate their generally infinite closure. Existential
witnesses depend on the universal assignment. Existing reasoning budgets
still apply. The Rust AST represents quoted graphs and rule sides as `Graph`
values with `universals`, `existentials`, and `triples`; `Term::formula` and
`Rule::new` also accept triple vectors.

### Date comparisons, scoped collection, and UUIDs

The six `math:` comparison predicates above compare `xsd:date` and `xsd:dateTime` literals by their parsed instants, including explicit UTC offsets. A date is treated as midnight; a value without an offset is treated as UTC. These literals can be compared with each other, but not with a plain string or number. Numeric and duration comparisons continue to use their own conversions.

`log:collectAllIn` returns one list containing all solutions of its scoped clause. A blank node written in that clause is an existential pattern; a blank node already bound from input data denotes that specific node. In particular, collecting two or three scalar matches no longer creates extra singleton-list answers.

`?term log:uuid ?id` returns a deterministic UUID-shaped **string** for a bound term. Eyeron hashes an IRI's text or a literal's lexical value with SHA-1; other term kinds use their debug representation. It takes the first 16 hash bytes and sets UUID version and variant bits. No namespace UUID is included, so this is not an RFC 4122 UUIDv5 calculation. The same input text gives the same string across runs, while literals with different datatypes but the same lexical value can give the same string. `log:skolem`, by contrast, returns an IRI.

These behaviors are covered by the regressions added in [PR #9](https://github.com/eyereasoner/eyeron/pull/9).

## Running a program

```bash
cargo run --release -- examples/socrates.n3
cargo run --release -- --proof examples/socrates.n3
```

Read from standard input with `-`; multiple files (and HTTP/HTTPS URLs) are merged into one document:

```bash
cargo run --release -- rules.n3 data.n3
cargo run --release -- rules.n3 https://example.org/data.ttl
```

RDF input is selected by extension for `.ttl`, `.nt`, `.nq`, and `.trig`; use `--rdf` when reading Turtle from standard input or when RDF-compatible output is required:

```bash
cargo run --release -- data.trig
cargo run --release -- --rdf - < data.ttl
```

Backward reasoning uses a conservative recursive-depth safety limit of 32 by default. Raise it for deliberately deep workloads without changing the library default:

```bash
cargo run --release -- --max-backward-depth 256 examples/backward.n3
```

### Resource limits

Non-terminating rule sets are ordinary N3, so a run is bounded rather than trusted. Every bound below is on by default and reported through `ReasonerResult::limits_reached` and `incomplete_summary()`, which turn a run that hit one into a structured incomplete result instead of a hang, an out-of-memory kill, or a panic. Embedders set them through `ReasonerOptions`; the command line exposes only `--max-backward-depth`.

| `ReasonerOptions` field | Default | Bounds |
|---|---|---|
| `max_iterations` | 1,000,000 | Fixpoint steps, counting outer passes and the agenda steps inside them. Because the agenda derives at most one fact per step, this is in practice a bound on the size of the closure. |
| `max_match_steps` | 200,000 | Matcher steps in one premise search. |
| `max_backward_depth` | 32 | Recursive backward-rule depth. |
| `max_backward_solutions_per_goal` | 1,024 | Substitutions retained for one backward goal. |
| `max_term_bytes` | 16 MiB | Term text in one derived fact. A rule that grows a term geometrically, such as one doubling a literal with `string:concatenation`, exhausts memory in a few dozen firings, which no step counter is quick enough to catch. |

Two further bounds are fixed rather than configurable, because passing them means the process would die rather than return an answer:

- **Terms nest at most 64 levels deep**, in input and in anything reasoning derives. Nesting is walked by recursion and exhausting the stack aborts the process, so deeper input is a parse error in every parser (N3, Turtle, TriG, N-Triples and N-Quads) and a deeper derived fact is dropped with `ReasonerLimit::TermDepth`. A rule that merely wraps a term, such as `{ :a :l ?x } => { :a :l (?x) }`, stays small in bytes while nesting one level per firing, so the byte bound alone would not stop it. The deepest nesting in the example and conformance corpora is 14 levels.
- **`string:format` refuses a field width beyond `max_term_bytes`' default**, so a format string cannot ask for a gigabyte of padding. Like any builtin call that cannot produce a value, such a call simply yields no binding.

A run that needs no bound at all still pays nothing for these: they are checks on counters the reasoner already keeps.

## RDF Messages

Eyeron recognizes RDF Message Logs containing a `VERSION "*-messages"` directive and `MESSAGE` or `@message .` boundaries. In normal mode, the complete log is exposed as a replay graph using the `eymsg:` vocabulary; every message receives an envelope and, for a non-empty payload, a named quoted formula that rules can inspect atomically with `log:includes`.

```bash
cargo run --release -- --rdf \
  examples/rdf-messages.n3 \
  examples/input/rdf-messages.trig
```

For message-at-a-time processing, use `--stream-messages`. Eyeron reads local-file or HTTP(S) input incrementally, reasons over each message with the supplied N3 program, writes that message's RDF result, and flushes the output before reading the next message:

```bash
cargo run --release -- --rdf --stream-messages \
  examples/alma-rdf-messages.n3 \
  tests/input/alma-rdf-messages-small.nt
```

Each streamed message is evaluated independently. The current streaming path does not retain derived facts between messages and does not accept the message log through standard input.

## Implementation notes

This section is a tour of the reasoner sources for readers modifying or extending the reasoner; see [the guide's repository map](guide.md#repository-map) for the shared `ast.rs` term model.

- **Lexing (`lexer.rs`)** turns source characters into a flat token stream (names, variables, literals, punctuation, formula braces, list parentheses, implication arrows), each token carrying a byte offset used later for line/column error reporting. Keeping lexing separate means the parser asks "is this an arrow token?" instead of repeatedly interpreting characters.
- **Parsing (`parser.rs`, `rdf_compat.rs`)** exposes `parse_n3`, `parse_n3_with_source` (for proof source locations), `parse_rdf12`, and `parse_rdf_message_log`. One `Parser` with a `ParserProfile` enforces different grammar restrictions for N3, Turtle, TriG, N-Triples, and N-Quads. Compact syntax such as a blank-node property list (`[ :name "Ada" ]`) expands into a generated blank node plus a triple, which is why several parsing functions return both a term and a vector of generated triples. Parenthesized lists, by contrast, stay first-class `Term::List` values rather than being lowered into `rdf:first`/`rdf:rest` triples — this avoids polluting rule conclusions and the fact closure with structural bookkeeping; rules that explicitly use `rdf:first`/`rdf:rest` or `list:` built-ins can still inspect a native list through the reasoner's virtual list matching (see below). RDF Message Logs are split at message boundaries, with each payload parsed into message-envelope vocabulary plus a quoted formula so rules can inspect a message as one atomic graph.
- **Reasoning (`reasoner.rs`)** is the largest module: the core fixpoint algorithm plus every built-in. `ReasonerResult` separates `explicit` (input facts), `derived` (newly inferred facts), `closure` (both), `proofs`, and completion status/statistics — which is why normal output does not repeat every input fact. `FactIndex` avoids a naive "scan every fact for every premise" matcher by storing fact positions under three maps (`predicate`, `(subject, predicate)`, `(predicate, object)`); its `candidates` method uses whichever pattern positions are already ground to select a small candidate set, falling back to a full scan when necessary. `match_term` handles unbound/bound pattern variables, element-by-element list matching, unordered-collection formula unification, and equality of concrete terms; `unify_term` (used when either side may contain a variable) additionally performs an **occurs check** to avoid cyclic substitutions such as `?x = (?x)`. For multiple premises, `match_premise_remaining` is a recursive backtracking search that reorders premises by selectivity (preferring a runnable, selective premise with few candidates) rather than blindly using source order — the same idea as join ordering in a relational database.
- **The forward-chaining fixpoint**: explicit facts seed the closure and indexes; each pass drives agenda-safe rules from newly added facts, evaluates other forward rules with general matching, instantiates conclusions, and inserts unseen facts (registering any newly generated rule) until nothing changes. A `HashSet<Triple>` named `seen` prevents duplicates and is also the fixpoint signal. Scoped built-ins whose answers depend on the *completed* current graph — rules using `log:collectAllIn`, `log:forAllIn`, or `log:notIncludes` — are deferred until ordinary forward reasoning reaches closure saturation, then re-evaluated (and, if they derive new facts, ordinary reasoning resumes before scoped built-ins run again); this prevents a temporary, incomplete closure from producing an aggregate or negative conclusion that a later fact could have invalidated. `AgendaIndex` maps a newly added fact directly to the rule premises it might satisfy, so a one-premise transitive chain processes each new fact once instead of rescanning all rules and facts every iteration; rules needing more context (certain multi-premise forms, built-ins, backward dependencies, blank-node conclusions) fall back to the general matcher, with both paths preserving identical logical behavior.
- **Backward rules**: `solve_backward_goal` recursively searches `<=` rules, which are **standardized apart** before use (variables renamed so separate rule applications cannot collide variables), with a recursion stack for cycle detection and depth/solution limits (`DEFAULT_MAX_BACKWARD_DEPTH: usize = 32` by default, raised with `--max-backward-depth`) bounding the search.
- **Built-ins**: `eval_builtin` dispatches by predicate IRI to functions covering arithmetic, string matching, list processing, time extraction, hashing, and formula inspection. A built-in consumes the current binding and returns zero (premise failed), one, or several possible result bindings — the same interface as ordinary fact matching, so both participate in the same backtracking search. `log:query` rules are held until the normal rules reach a fixpoint, since they select/format results without feeding output back into reasoning; a conclusion using `log:outputString` is treated specially by the printer and emitted as plain text.
- **Proofs (`proof.rs`)**: when `ReasonerOptions::proof` is enabled, each derived fact can retain the fact, the rule that fired, the instantiated premises, and the bindings. `proof_to_n3` groups these `DerivedFact` records, connects derived premises to their own derivations, and distinguishes explicit facts, built-in steps, and unproven steps. One walk covers every claim at once, so a premise shared by several derivations is written once rather than once per claim, and each step is an ordinary top-level triple whose subject is its quoted conclusion. Every step carries exactly one predicate saying why it holds — `pe:rule N` for a rule the engine applied, naming it by its number in the document, or `pe:fact "file"`, `pe:builtin` or `pe:unproven` — followed by `pe:binding` and `pe:uses`. See [the guide's proof section](guide.md#proofs). Proof collection is optional because retaining derivation history costs memory.
- **Output (`printing.rs`)** reverses part of parsing: only prefixes actually used in the result are printed (the printer first walks the output to collect used namespaces), and `result_to_string`/`rdf_result_to_string` look for `log:outputString` first, falling back to normal triple serialization. `triples_to_n3`/`triples_to_trig` insert a blank line around any triple whose own rendering spans multiple lines (a quoted-formula subject/object, an implication, a named-graph block), so such a triple gets its own paragraph instead of crowding a neighboring one-line triple; ordinary one-line triples otherwise print back to back with no separator.

Several broader ideas recur across the implementation: separation of concerns (lexing/parsing/evaluation/proof/serialization are separate modules), algebraic data types (`Term` as a Rust enum), hashing and ordering (sets for fast duplicate detection, ordered maps for stable behavior), database techniques (indexes and selective join ordering), search algorithms (backtracking premise matching, bounded depth-first backward search), fixed-point computation (forward chaining monotonically grows a set until it stops changing), and resource safety (explicit limits turn nontermination into a structured incomplete result rather than a hang).

## Known limitations

- `-s` / `--stream` is retained for command-line compatibility but ordinary N3 output is still emitted after the fixpoint.
- Streamed RDF Messages are independent: no persistent cross-message fact store or window state is maintained, and stdin is not supported by `--stream-messages`.
- `log:content`, `log:semantics`, and `log:semanticsOrError` do not dereference arbitrary network resources; their external-resource behavior is deterministic and limited to the bundled conformance cases.
- Persistent stores and custom external built-in modules are not implemented.
- Proof output does not yet include every possible trace comment or explanation detail.
- Eyeron implements the N3 features and built-ins listed above, not every extension in every historical N3 implementation.
